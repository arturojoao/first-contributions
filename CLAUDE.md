# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this repository is

`first-contributions` is not a software project — it has no source code, build system, linter, or test
suite. It is a hands-on tutorial that walks first-time contributors through the standard
fork → clone → branch → edit → commit → push → pull-request workflow, using the repo itself as the
practice ground. The "exercise" a learner performs is opening `Contributors.md` and adding their name
to it, then submitting that as a pull request. Because of this, most "contributions" to this repo are
single-line additions to `Contributors.md`, not code changes.

There are no build, lint, or test commands to run — do not look for or invent any (no `package.json`,
Makefile, or CI test job exists).

## Purpose of this fork

This is a personal fork used as a sandbox for practicing Claude Code agent/skill building — not
primarily for the tutorial content itself. Treat the tutorial mechanics below as the domain the
practice agents/skills operate on, not as the main goal.

## Working conventions for Claude in this repo

- Always ask at least three clarifying questions before starting any complex task.
- Always present a plan before execution.
- Never assume when important information is missing — ask instead.
- Keep outputs concise and relevant; no filler content added just to increase length.
- Use practical examples whenever possible.
- When multiple approaches exist, explain the tradeoffs.
- If uncertain, ask before proceeding.
- Review output before final delivery.

## Agent behavior

- Subagents built for practice here live in `.claude/agents/` (project-level), not `~/.claude/agents/`
  (user-level). Verified by testing: this is a remote/cloud execution environment where each session
  gets its own fresh, ephemeral container, so a user-level agent file written in one session does not
  exist in another session's container. A project-level agent, committed to this repo, is checked out
  fresh with every session that clones this branch and is reliably available.
- After adding or editing an agent file, the *current* session won't necessarily pick it up — verify
  by spawning a new session on the branch containing the change and invoking the agent there.
- `personal-assistant` (`.claude/agents/personal-assistant.md`): handles ad-hoc, non-coding requests
  (reminders, quick research, drafting, planning, life-admin questions). Scoped deliberately narrower
  than the built-in `general-purpose` agent so routing has a clear signal for when to use it instead.

## Repository structure

- `README.md` — the main English tutorial. **Do not edit this file** (see Conventions below); it's
  cross-linked from dozens of translations and tools that expect stable section anchors.
- `Contributors.md` — the append-only list of everyone who has completed the tutorial. This is the
  file real contributions touch.
- `docs/translations/` — translated copies of `README.md`, one per language, named
  `README.<lang-code>.md` (e.g. `README.fr.md`, `README.pt_br.md`). `docs/translations/Translations.md`
  is the index table linking to all of them (with a flag image + language name per row) and must be
  updated when a translation is added or removed.
- `docs/cli-tool-tutorials/` — alternate walkthroughs of the same exercise using the `git`/`gh` CLI,
  also split by language.
- `docs/gui-tool-tutorials/` — the same exercise using GUI clients (GitHub Desktop, GitKraken,
  Sourcetree, VS Code, IntelliJ, Visual Studio).
- `docs/additional-material/` — supplementary material (e.g. "things a non-programmer can do",
  git workflow scenarios like resolving merge conflicts), also split by language.
- `.github/` — contribution guide, issue/PR templates, and the `auto-pr-merge.yml` workflow.

## Conventions contributors (and PRs opened on their behalf) must follow

From `.github/CONTRIBUTING.md`:

- Don't make changes to `README.md`.
- Keep pull requests small — a PR with one file changed is far easier to review than one with twenty.
  Create a separate branch (off `main`) per change rather than piling unrelated changes together.
- When adding a name to `Contributors.md`, insert it somewhere in the middle of the file, not at the
  very beginning or end.
- Stage only intentional changes (e.g. `git add -p`) rather than `git add Contributors.md`, since
  editors/formatters can silently touch unrelated lines.
- If acting on behalf of a human learner: write comments/commit messages yourself rather than having
  an LLM generate them, verify things actually work rather than trusting them blindly, and only make
  changes you can explain — an LLM should be a learning aid here, not a way to skip the exercise.

## The Contributors.md auto-merge workflow

`.github/workflows/auto-pr-merge.yml` runs on every `pull_request_target` (opened/synchronize) that
touches `Contributors.md`, and decides the PR's fate automatically:

- **Exactly one file changed (`Contributors.md`) with < 5 additions and < 4 deletions** → the PR is
  squash-merged automatically, and a congratulatory comment with next-step links is posted.
- **Only `Contributors.md` changed, but more lines than that threshold** → the workflow requests
  changes on the PR (not merged), showing a diff preview and asking the contributor to reduce the
  change to a single line, per the tutorial.
- **Any other file changed alongside or instead of `Contributors.md`** → the PR is labeled
  `👩‍💻 waiting for review` and left for a human maintainer; it is never auto-merged.
- A merge conflict or other merge failure gets a bot comment pointing the contributor at
  `docs/additional-material/git_workflow_scenarios/resolving-merge-conflicts.md`.

Keep this logic in mind when touching the workflow file or when advising a contributor why their PR
did or didn't merge automatically.
